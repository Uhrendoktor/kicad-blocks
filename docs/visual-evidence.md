## How the images are produced

CI launches the production Tk dialogs under a virtual display and exports the facade and implementation with KiCad CLI. It records the source commit and SHA-256 hashes in a manifest. The publishing step verifies those hashes before updating the separate `docs/previews` branch. Pull-request runs upload the same files as workflow artifacts.

The capture tests check that windows are visible, images are non-blank, and the scripted chooser selection returns the expected profile, variant and parameter. These screenshots demonstrate rendered UI states; they do not claim that every editor operation is fully automated.

## What CI does and does not verify

CI checks the block browser, folder manager, task hub, creation form, variant editor, instance configuration, native symbol chooser handoff, project-library registration and schematic/PCB operations.

Some manual validation is still useful:

- A complete live Symbol Editor save/edit/publish sequence is not automated.
- The PCB imported-group action is tested, but the full mouse-driven commit/cancel interaction is not automated end to end.
- Recursive hierarchical extraction is tested with a two-level fixture. A complex, multi-sheet design should still be opened and reviewed manually.

## Regenerate the previews locally

Use the supported KiCad CLI, Tkinter, Xvfb, xdotool, Pillow and CairoSVG:

```bash
python -m pip install cairosvg pillow
xvfb-run -a -s "-screen 0 1600x1000x24" \
  python tests/capture_visual_docs.py --output-dir artifacts/visual-docs
```

Treat the generated files as build outputs. When a UI changes, update the code or capture fixture and let CI regenerate the screenshots; do not edit the published images by hand.
